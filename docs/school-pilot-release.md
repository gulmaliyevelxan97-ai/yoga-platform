# Закрытое тестирование RESTART School

Публичный сайт и локальная PWA выходят отдельно от облачного пилота. Контрольные точки для возврата клиентского кода: основной сайт b98336a, облачный пилот 2fcc784. Пилот собирается из отдельной ветки; в обычной конфигурации облачный клиент отключён.

## Зависимости

| Модуль | Зависит от | Хранит |
| --- | --- | --- |
| Аккаунт | Supabase Auth, подтверждение почты, PKCE и точный URL возврата | Сессию клиента |
| Личные данные | Пользовательский JWT, миграции 001–003, RLS | Профиль, цели, настройки, дневник, историю и маркеры удаления |
| Академия | Личные аккаунты, миграция 004 | Роли, зачисления, программы, модули, уроки и завершения |
| Расписание | Роли Академии, миграция 005 | События, вместимость, бронирования и посещаемость |
| Входящие и показатели | Академия и расписание, миграция 006 | Согласие, персональные события и вычисляемые агрегаты |
| Мобильный интерфейс | Браузерный клиент, manifest и service worker | Статическую оболочку для офлайна |

## Облако перед первым тестом

1. Владелец уже установил три исходные миграции. Для их проверки в SQL Editor служит запрос `supabase/checks/installed_cloud.sql`. Десять значений true проверяют перечисленные права и RLS. Активацию hook подтверждают в настройках Auth.
2. В панели проекта проверьте Authentication → Hooks → Before User Created → Postgres → public.restart_before_user_created. Сверьте статус и сохранённую функцию. Переключатель общей регистрации до проверки оставьте закрытым.
3. Для отдельной пилотной сборки возьмите Project URL непосредственно из Connect этого проекта и ключ sb_publishable_ из настроек API. Настройте email confirmation и точный HTTPS redirect пилота. Порядок сборки описан в restart-cloud-pilot.md.
4. Перед установкой дополнительных миграций проверьте доступность резервной копии в Database → Backups, дату копии и возможность восстановления. Для проекта без подходящей копии подготовьте зашифрованный логический экспорт вне GitHub и тестовое восстановление в отдельную БД. Проверьте отдельно auth, данные public и restart_private, права, функции, триггеры и настройки Auth. Зафиксируйте, как восстановите идентификаторы пользователей. Наличие коммита Git подтверждает сохранность исходников, для данных нужна отдельная проверка.
5. Новые SQL-файлы примените сначала только к тестовой базе с эквивалентными схемой Auth и привилегиями. Проверьте учебную роль A и роль B через реальные JWT, отдельно роль преподавателя и администратора. Первый администратор назначается оператором базы по подтверждённому UUID.
6. Критерии допуска: проверенная отправка и возврат письма, блокировка адреса вне списка именно hook, восстановление пароля, две независимые сессии, конфликт правок, отзыв доступа к уроку, конкурентная запись на последнее место, работа после потери сети и перезапуска установленной PWA. Тестовые данные и расписание должны быть изолированы от реальных учеников.

## Откат

При ошибке приостановите пилотный клиент и верните предыдущий проверенный клиентский артефакт. Оставьте RLS и ограничения регистрации включёнными. Смена клиентской версии сохраняет данные в базе. Для исправления схемы подготовьте новую прямую миграцию. Удаление таблиц и восстановление всей базы требуют отдельного решения: восстановление снимка может потерять записи, созданные после него. Перед восстановлением сохраните текущее состояние и проверьте процедуру на отдельной копии.
