# Закрытый пилот RESTART Cloud

Ветка содержит только код и миграции. Обычная сборка использует `app/cloud-config.mjs` со значением `null` и продолжает работать локально. Публичный GitHub Pages не является тестовой средой для регистрации.

## Состояние проекта restart-app

Владелец подтвердил установку миграций 20261120000100–20261120000300, наличие первого тестового адреса и включение **Before User Created** с типом **Postgres** и функцией **public.restart_before_user_created**. Для действующего проекта проверьте настройки возврата и доставки почты в шагах 5–6, затем соберите закрытый пилот. Шаги создания схемы и настройки hook относятся к новой среде. Миграции 004–006 пока проверены локально.

## 1. Подготовить Supabase

1. В проекте `restart-app` откройте **Connect**. Запишите **Project URL** и **Publishable key** с префиксом `sb_publishable_`. Если в окне показан другой тип ключа, откройте **Settings → API Keys → Publishable and secret API keys**. Для клиентской сборки нужны только эти два значения.
2. Пока настройка не завершена, в **Authentication → Sign In / Providers** оставьте регистрацию выключенной. План рассчитан на **Email + password**, с подтверждением email и минимальной длиной пароля 12. Оставьте анонимный вход и дополнительные провайдеры выключенными.
3. Запустите [предварительную проверку](../supabase/checks/preflight.sql) в **SQL Editor**. Запрос только читает системный каталог. Пустой результат означает, что перечисленные имена свободны, а необходимые роли и объекты Supabase на месте. При любом результате с предупреждением остановитесь и уточните состояние проекта. Затем примените три миграции по порядку. Предпочтительно использовать [Supabase CLI](https://supabase.com/docs/guides/local-development/database-migrations) на компьютере от имени уполномоченного пользователя. Из корня репозитория:

   ```sh
   supabase login
   # Если supabase/config.toml ещё отсутствует:
   supabase init
   supabase link --project-ref <PROJECT_REF>
   supabase db push --dry-run
   supabase db push
   ```

   `PROJECT_REF` — часть Project URL перед `.supabase.co`. Проверьте, что dry run показывает только три миграции RESTART. Пароль базы при необходимости вводите в подсказку CLI. На телефоне альтернатива — открыть **SQL Editor → New query** и запустить содержимое каждого файла целиком, по одному, в указанном порядке:

   - [20261120000100_restart_student_data.sql](../supabase/migrations/20261120000100_restart_student_data.sql)
   - [20261120000200_restart_import_local.sql](../supabase/migrations/20261120000200_restart_import_local.sql)
   - [20261120000300_restart_pilot_signup.sql](../supabase/migrations/20261120000300_restart_pilot_signup.sql)

   SQL Editor не записывает эти файлы в историю CLI. Если использовали редактор, перед будущим `db push` сверьте схему и отметьте уже применённые версии через `supabase migration repair --status applied 20261120000100 20261120000200 20261120000300`. Повторно запускать эти SQL-файлы не требуется.
4. В **Authentication → Hooks** настройте **Before User Created Hook** с типом **Postgres**, схемой `public` и функцией `restart_before_user_created`. Добавьте только согласованные тестовые адреса через SQL Editor. В примере `example.invalid` нужно заменить на реальный тестовый адрес, доступный владельцу:

   ```sql
   insert into restart_private.pilot_emails (email)
   values (lower(btrim('tester@example.invalid')))
   on conflict do nothing;
   ```

   Таблица закрыта для браузерных ролей. Если проект уже обслуживает другой продукт, сначала оцените влияние, поскольку Auth Hook и настройки регистрации действуют на весь проект.
5. В **Authentication → URL Configuration** задайте `Site URL` и точный разрешённый URL возврата для пилота, например `https://<пилотный-хост>/app/`. Не добавляйте публичный URL текущего приложения. Для локальной проверки можно отдельно добавить `http://localhost:4173/app/`. Ссылки подтверждения и восстановления нужно открыть в том же браузере и профиле, где запустили запрос PKCE.
6. Проверьте доставку писем. Штатный SMTP Supabase ограничен авторизованными адресами команды. Для тестировщиков вне команды настройте доверенный SMTP через **Authentication → Emails → SMTP Settings**. Учётные данные SMTP остаются в Supabase. В проекте с отключённой саморегистрацией сохраните это ограничение. Сценарий проверки без отправки писем приведён ниже.

## 2. Собрать закрытый пилот

Нужны Node.js и npm. Используйте переменные окружения закрытой среды сборки или локальной машины. `Project URL` и `sb_publishable_…` — конфигурация, которую браузер получает по назначению. Пароль базы, `sb_secret_…`, `service_role`, токены управления и SMTP-пароли в сборку не передаются.

```sh
npm ci
npm test
npm run build:pilot -- --verify
# Установите RESTART_SUPABASE_URL и RESTART_SUPABASE_PUBLISHABLE_KEY
# в окружении закрытой среды сборки.
npm run build:pilot
```

Пилот собирается в новый каталог `dist/` и открывается по `/app/`. Для повторной сборки задайте `RESTART_PILOT_OUTPUT` с путём к ещё не существующему каталогу внутри уже существующего родительского каталога. Для локального запуска из корня репозитория выполните `python -m http.server 4173 --bind 127.0.0.1 --directory dist` и откройте `http://localhost:4173/app/`. Для телефона нужен отдельный HTTPS-хост, разрешённый только тестировщикам. Публичный GitHub Pages при этом остаётся на прежнем релизе. Добавьте защиту самого предрелизного хоста при его настройке.

## Почта и первый закрытый запуск

В **Authentication → Emails → SMTP Settings** проверьте, включён ли Custom SMTP. Если он выключен и отдельный Send Email Hook отсутствует, действует встроенная служба Supabase. В **Organization Settings → Team** достаточно сверить, совпадает ли адрес владельца в команде с разрешённым тестовым адресом. Список допущенных к регистрации и список получателей встроенной почтовой службы проверяются отдельно. Встроенный SMTP подходит для бесплатной попытки, если адрес входит в команду. Учитывайте лимит в два письма в час и проверяйте результат в почте и Auth Logs. [Ограничения Supabase](https://supabase.com/docs/guides/auth/auth-smtp)

Если адрес вне команды, используйте после согласования SMTP со своим подтверждённым отправителем. Resend Free предоставляет 100 писем в сутки и 3 000 в месяц. Для отправки на внешний адрес требуется подтверждённый собственный домен. Brevo Free предоставляет 300 писем в сутки и требует настроить отправителя и аутентифицировать домен. SMTP-настройки заполняются только в Supabase Dashboard. Клиентский код, миграции и полномочия команды для этого не меняются. Если домена нет, сначала проверьте встроенную службу для существующего командного адреса. [Resend](https://resend.com/pricing) · [Brevo](https://help.brevo.com/hc/en-us/articles/208580669-FAQs-What-are-the-limits-of-the-Free-plan)

Адрес на машине, которая запускает сервер, — **http://localhost:4173/app/**. Для Samsung с реальной почтой нужен отдельный HTTPS-стенд с контролем доступа. Его точный URL появится после выбора закрытого хоста. Используйте одинаковые браузер, профиль и адрес приложения для запроса и открытия ссылки. Проверьте настройки **Confirm email**, **Site URL** и **Redirect URLs** до отправки. Первая регистрация, письмо подтверждения и сброс пароля требуют согласования владельца.

До отправки писем можно проверить установленную SQL-функцию под ролью Auth. Запустите в SQL Editor, заменив `tester@example.invalid` на разрешённый тестовый адрес. Транзакция доступна только для чтения. Результат состоит из двух логических значений. Этот запрос проверяет решение функции, а сквозной вызов hook при регистрации проверяется отдельно.

```sql
begin read only;
set local role supabase_auth_admin;
select public.restart_before_user_created(
  jsonb_build_object('user', jsonb_build_object('email', 'tester@example.invalid'))
) = '{}'::jsonb as allowed,
coalesce(public.restart_before_user_created(
  '{"user":{"email":"restart-not-allowed@example.invalid"}}'::jsonb
) #>> '{error,http_code}' = '403', false) as rejected;
rollback;
```

## 3. Проверить перед допуском учеников

1. В `restart-app` запустите только [проверку установленных объектов](../supabase/checks/installed_cloud.sql) в **SQL Editor**. Ожидаются десять строк со значением `true`. Этот запрос проверяет RLS и права, а включение hook подтверждает Dashboard.
2. Проверьте, что подтверждение email включено, а анонимный вход и лишние провайдеры выключены. Начните с одного разрешённого владельцем адреса и одного нового, контролируемого владельцем адреса вне списка. Если саморегистрация отключена, этот проект не позволяет проверить вызов hook через форму регистрации. Оставьте настройку как есть и зафиксируйте блокировку. Проверку через Auth можно провести на согласованном закрытом стенде с такой же конфигурацией.
3. В форме закрытого пилота подайте один запрос регистрации на адрес вне списка. Ожидается отказ `Signup is unavailable.` от hook. В **Authentication → Users** новой записи быть не должно. Если ответ относится к отключённой регистрации, CAPTCHA или SMTP, результат проверки hook не засчитывается.
4. Подайте запрос с разрешённого адреса. Убедитесь, что письмо пришло и открыло тот же пилот в том же браузере и профиле. Проверьте, что адрес подтверждён в Dashboard, затем выйдите и войдите с тем же паролем.
5. После выхода запросите восстановление и откройте письмо в том же браузере. До задания нового пароля должен отображаться экран восстановления без доступа к дневнику и истории. После сохранения проверьте, что старый пароль отклонён, а новый работает. Завершайте каждый запрос подтверждения или восстановления до запуска следующего в том же профиле браузера. Ссылка и одноразовый код остаются у владельца.

## 4. Проверить синхронизацию и изоляцию

- Для второго тестового аккаунта согласуйте ещё один адрес. Адрес из теста отказа можно добавить в список только после фиксации отрицательного результата и отдельного допуска владельцем.
- Пользователь A сохраняет тестовое имя, цель, заметку без личных сведений и завершает практику. Пользователь B не видит записи A и не может читать или изменять их через API со своим токеном. Запросы без сессии получают отказ. Проверить во всех пяти таблицах и при вызове импорта.
- Один аккаунт входит на двух устройствах. После входа, возврата в активную вкладку без формы или нажатия **Обновить данные** видны данные, записанные на другом устройстве. Одновременное изменение одной записи проверяется по ревизии. Это обновление снимков, без подписки на события в реальном времени.
- Создайте локальную запись в гостевом режиме пилота. Войдите и подтвердите импорт в **Аккаунт**. Повторный импорт не создаёт дубли и не меняет существующие облачные записи. После удаления облачной заметки повторный импорт не восстанавливает её. После выхода локальная версия остаётся доступной. Браузер не разделяет локальные записи между разными хостами. Для переноса данных с действующего сайта в будущей согласованной версии нужен тот же origin либо отдельный экспорт и импорт.
- Проверьте восстановление доступа после просрочки сессии, открытие без сети и повторное подключение. Облачный снимок хранится в памяти вкладки. Облачные изменения требуют сети и не попадают в очередь. Прежний локальный режим остаётся офлайн-доступным. Service worker хранит только статические ресурсы, без ответов Supabase и содержимого дневника.
- Согласуйте сроки хранения, удаление аккаунта и резервные копии до обработки данных настоящих учеников. Удаление облачной заметки очищает текст и оценки и оставляет техническую запись для дедупликации. При удалении аккаунта пользовательские строки удаляются каскадно. Самостоятельное удаление аккаунта через UI в пилот не входит.
